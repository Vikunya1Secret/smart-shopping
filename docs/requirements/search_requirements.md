# Детальные требования к поиску и адаптерам источников

**Проект:** Умный Шопинг
**Функции:** M2.1, M2.5, M3.1
**Связанные требования:** FR-1, FR-2, FR-3, NFR-1, NFR-6, NFR-7
**Автор:** Клейн А.Н.
**Статус:** черновик, значения помечены «предложено» и требуют согласования с бэкенд-разработчиком

## 1. Входные данные поиска

| Параметр | Тип | Обязательность | Правило |
|---|---|---|---|
| query | строка | да | 2–200 символов, не пустая после удаления пробелов |
| region | строка | нет | город или индекс; если не указан, берётся из профиля, для гостя используется регион по умолчанию |
| user_id | число | нет | передаётся для авторизованного пользователя (профиль, история) |

Запрос принимается в двух формах: естественный язык («смартфон с хорошей камерой до 50 000 рублей») и точное название или артикул. На этапе MVP разбор бюджета и атрибутов из текста (M2.2) не выполняется, запрос передаётся источникам как есть.

## 2. API поиска

| Метод | Назначение | Результат |
|---|---|---|
| `POST /search` | создать поиск | `search_id` и статус `running` |
| `GET /search/{id}/results` | получить результаты | предложения, полученные на текущий момент, и статус поиска |

**Статусы поиска:** `running` (идёт), `partial` (есть часть результатов), `done` (все источники ответили или истёк таймаут), `empty` (ничего не найдено), `error` (все источники недоступны).

Клиент опрашивает `GET /search/{id}/results` с интервалом около 1 с (предложено) до статуса `done`, `empty` или `error`.

## 3. Требования к адаптеру источника (M3.1)

Каждый источник подключается как отдельный адаптер с единым интерфейсом (NFR-6).

| Метод адаптера | Что делает |
|---|---|
| `search(query, region)` | возвращает список «сырых» предложений источника |
| `get_name()` | название и тип источника (API, фид, парсинг, мок) |
| `is_available()` | проверка доступности источника |

**Правила работы**
- Таймаут одного источника: 5 секунд (предложено), чтобы общий ответ уложился в 10 секунд (NFR-1).
- Повторы при ошибке: не более 1 повтора (предложено).
- Запросы ко всем источникам выполняются параллельно.
- Ошибка или таймаут одного адаптера не прерывает поиск, остальные результаты возвращаются (NFR-7).
- Адаптер возвращает данные в своём формате, приведение к единому формату выполняет слой нормализации (см. `offer_data_spec.md`).
- Для разработки допустимы адаптеры с тестовыми фидами и мок-данными, помеченные типом `mock`.

## 4. Требования к выдаче

- Минимум 3 источника на запрос к концу недели 3, к концу недели 2 минимум 2 (план работ).
- Каждое предложение содержит: цену, наличие, продавца, рейтинг продавца, ссылку (FR-3).
- Условия возврата и гарантия передаются, если источник их предоставляет (FR-4).
- Частичные результаты отдаются по мере ответа источников (M2.5).
- Полное время ответа не более 10 секунд (NFR-1).

## 5. Поведение в нештатных ситуациях

| Ситуация | Ожидаемое поведение |
|---|---|
| Пустой запрос | ошибка валидации 400, понятное сообщение |
| Один источник не ответил | поиск продолжается, статус `partial` или `done` |
| Все источники недоступны | статус `error`, сообщение пользователю |
| Источник вернул 0 предложений, остальные нет | поиск успешен, пустой источник игнорируется |
| Ни один источник ничего не нашёл | статус `empty`, сообщение «Ничего не найдено» |

## 6. Чек-лист приёмки недели 2

- [ ] `POST /search` принимает запрос и возвращает `search_id`
- [ ] `GET /search/{id}/results` возвращает предложения
- [ ] Данные приходят минимум из 2 источников
- [ ] Отключение одного источника не ломает выдачу
- [ ] Время ответа на тестовых запросах не более 10 секунд
- [ ] Результаты в едином формате (см. `offer_data_spec.md`)
