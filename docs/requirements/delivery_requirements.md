# Требования к расчёту доставки

**Проект:** Умный Шопинг
**Функции:** M4.1 (регион), M4.2 (стоимость), M4.3 (сроки); частично M4.5, M4.6
**Связанные требования:** FR-6, FR-7, NFR-1, NFR-7
**Автор:** Клейн А.Н.
**Дата:** 16.11.2026
**Статус:** черновик на согласование с бэкенд-разработчиком. Значения, помеченные «предложено», условные и подлежат замене реальными тарифами.

## 1. Назначение

Для каждого найденного предложения система рассчитывает стоимость и срок доставки в регион пользователя. Эти данные входят в итоговую цену (товар + доставка) и в индекс выгоды, поэтому от их корректности зависит качество рекомендации. Критерий приёмки заказчика: «Система автоматически рассчитывает стоимость доставки из каждого магазина с учётом региона пользователя».

|---|---|---|
| M4.1 Выбор региона | Must | да |

## 3. Определение региона (M4.1)

**Требования**
- Пользователь выбирает регион вводом города или индекса с подсказками из списка.
- Для авторизованного пользователя регион сохраняется в профиле (поле из M1.2) и подставляется автоматически.
- Для гостя регион хранится на время сессии.
- Если регион не указан, используется регион по умолчанию: Москва (предложено), и интерфейс показывает, какой регион применён.
- Смена региона пересчитывает доставку у всех предложений в выдаче без нового запроса к источникам.
- Автоопределение региона по геолокации не входит в MVP.

**Тарифные зоны (предложено)**

Чтобы не вести тариф для каждого города, регионы объединяются в 5 зон:

| Зона | Примеры | Коэффициент стоимости | Срок транспортировки, дней |
|---|---|---|---|
| 1 | Москва, Санкт-Петербург | 1,0 | 1–2 |
| 2 | Центральная Россия | 1,5 | 2–3 |
| 3 | Урал, Поволжье | 2,0 | 3–4 |
| 4 | Сибирь | 3,5 | 5–7 |
| 5 | Дальний Восток | 6,5 | 7–10 |

Коэффициенты подобраны так, чтобы воспроизводить пример из описания заказчика: доставка в Москву около 150 рублей, во Владивосток около 1000 рублей (150 × 6,5 = 975). Реальные значения будут получены из тарифов служб доставки или от продавцов и внесены администратором (M9.2).

## 4. Расчёт стоимости (M4.2)

**Порядок источников данных (по убыванию приоритета)**
1. Стоимость и срок доставки, которые отдаёт сам магазин или источник для выбранного региона.
2. Расчёт по тарифной таблице проекта.
3. Значение по умолчанию (стоимость по зоне 1), с пометкой «оценочно».

**Формула расчёта по тарифной таблице (предложено)**

```
стоимость_доставки = базовый_тариф × коэффициент_зоны × коэффициент_габарита
```

| Параметр | Значение (предложено) |
|---|---|
| Базовый тариф | 150 ₽ |
| Габарит малый | 1,0 |
| Габарит средний | 1,5 |
| Габарит крупный | 3,0 |

**Бесплатная доставка**
- Если источник сообщает о бесплатной доставке, стоимость равна 0.
- Если у продавца задан порог (например, «бесплатно от 5 000 ₽»), стоимость равна 0 при цене товара не ниже порога.
- В интерфейсе бесплатная доставка отмечается явно.

**Итоговая цена**

```
итоговая_цена = цена_товара + стоимость_доставки
```

Итоговая цена используется для сортировки, фильтров и индекса выгоды.

## 5. Оценка сроков (M4.3)

```
срок = срок_обработки_у_продавца + срок_транспортировки_по_зоне
```

- Срок обработки: берётся из данных источника, если нет, то 1–2 дня (предложено).
- Срок транспортировки: по таблице зон (раздел 3).
- Срок хранится как диапазон: минимум и максимум дней.
- Для сортировки и индекса выгоды используется верхняя граница диапазона (осторожная оценка, предложено).
- В интерфейсе срок показывается диапазоном, например «3–5 дней».

## 6. Прозрачность (M4.6)

- Если стоимость или срок получены из тарифной таблицы или значения по умолчанию, рядом отображается пометка «оценочно».
- Если данные пришли от магазина, пометка «по данным магазина».
- В карточке предложения показывается разбивка: цена товара, доставка, итого.

## 7. Структура результата

Расчёт сохраняется в сущности `DeliveryEstimate` (из модели данных отчёта по проектированию):

| Поле | Тип | Описание |
|---|---|---|
| offer_id | число | идентификатор предложения |
| region | строка | регион пользователя |
| zone | число | тарифная зона |
| cost | число | стоимость доставки в рублях |
| is_free | логическое | бесплатная доставка |
| days_min | число | минимальный срок, дней |
| days_max | число | максимальный срок, дней |
| estimate_source | перечисление | `store` (данные магазина), `tariff` (таблица), `default` |
| is_estimate | логическое | показывать пометку «оценочно» |
| calculated_at | дата и время | UTC, ISO 8601 |

## 8. Нештатные ситуации

| Ситуация | Ожидаемое поведение |
|---|---|
| Регион не указан | применяется регион по умолчанию, пользователь видит это |
| Регион не найден в справочнике | предлагается выбрать из подсказок, расчёт не выполняется |
| Источник не отдал данные о доставке | расчёт по тарифной таблице, пометка «оценочно» |
| Нет тарифа для зоны | значение по умолчанию, пометка «оценочно», запись в лог |
| Магазин не доставляет в регион | предложение помечается «доставка в регион недоступна» и не участвует в рекомендации |
| Самовывоз | стоимость доставки 0, срок определяется данными источника |
| Крупногабаритный товар | применяется коэффициент габарита 3,0 |

## 9. Нефункциональные требования

- Расчёт доставки для всей выдачи не должен добавлять более 1 секунды ко времени ответа (предложено; общий лимит 10 секунд, NFR-1).
- Тарифная таблица кэшируется (см. требования к кэшу, M3.5).
- Сбой расчёта для одного предложения не ломает выдачу: предложение показывается с пометкой «оценочно» (NFR-7).
- Региональные коэффициенты редактируются администратором без изменения кода (M9.2, Should).

## 10. Критерии приёмки

- [ ] Регион выбирается в интерфейсе и сохраняется в профиле
- [ ] Для каждого предложения выдачи рассчитаны стоимость и срок доставки
- [ ] Смена региона меняет стоимость и срок
- [ ] Бесплатная доставка и пороги учитываются
- [ ] Итоговая цена равна сумме цены товара и доставки
- [ ] Оценочные значения помечены
- [ ] Недоступность доставки в регион обрабатывается без ошибок

## 11. Открытые вопросы

1. Какие источники реальных тарифов будут использованы (API служб доставки или таблицы тарифов)? Решение зависит от результатов проверки источников.
2. Согласовать с бэкенд-разработчиком зоны, коэффициенты и значение «по умолчанию».
3. Нужна ли в MVP учёт габаритов, если источники не отдают размеры товара?
